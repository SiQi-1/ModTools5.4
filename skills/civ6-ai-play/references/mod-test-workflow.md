# 文明6 Mod 测试工作流：可靠、可重复、防漏判

适用：给一个“功能很多、细节很多”的文明6 Mod 建立可持续的测试体系。本文只讲**怎么测、怎么判断、怎么防止漏判**，不放某一次测试的具体结论；具体运行时技巧见 [真实 Mod 运行时验证](mod-runtime-testing.md)，通用分层见 [Mod 测试方法](mod-testing.md)。

一句话：**以“能力组”为计划单位，以“契约”为验收依据，以“断言 + 证据”为判定标准，以“覆盖矩阵 + 双向完备性检查”为防漏判机制。**

---

## 1. 六个分层（结论必须分层记录）

| 层 | 看什么 | 典型证据 | 不能证明什么 |
|---|---|---|---|
| 加载层 | Mod 是否被游戏加载、有无 Invalid reference/Database/Localization 错误 | `Modding.log`、`Database.log`、`Startup.log` | 不证明功能生效 |
| 数据层 | 真实加载后的 `GameInfo` 行（不是生成 SQL） | Tuner 读 `GameInfo.*`、构建产物哈希 | 不证明运行逻辑正确 |
| **对象层** | 对象（player/city/unit/district/plot）上的 **modifier 实例列表、owner/subjects、active、条件状态、栈/一次性** | `GameEffects.GetModifiers()` 等对象列表 dump | 不证明数值效果（但“挂对且启用”通常即可信，见 §4.6） |
| 逻辑层 | Lua/GP 状态、属性、建筑、单位、事件链 | 属性快照、单位/城市状态、日志 marker | 不证明玩家看得到 |
| 表现层 | UI 面板与交互 | `DoLeftClick` 前后截图、控件状态 | 不证明数值/规则正确 |
| 系统层 | AI 自动对局、长时间运行 | 看海日志、Runtime Error 计数、回归快照 | 不能替代逐能力验收 |

**判定纪律**：一条能力写“通过”，至少要有“数据层/对象层或逻辑层 + 表现层（若可见）”的证据；只凭某一层，只能记为“未验证”。**Modifier 型能力允许以“对象列表（挂对且 active）”作为主证据，不必强测数值效果**（依据见 §4.6 的前置信任模型）。

---

## 2. 能力组模型：测试计划的最小单位

不要按修改器/数据行排测试，按玩家能感知的**能力组**排：

| 组类型 | 组内成员示例 |
|---|---|
| 文明能力组 | 文明特性、核心系统入口 |
| 领袖能力组 | 每位领袖的主动/被动/UI 按钮 |
| 特色单位组 | 单位能力、战斗行为、地图交互 |
| 特色区域组 | 区域本体+建筑链+区域能力 |
| 特色建筑组 | 每个建筑的产出/限制/前置 |
| 改良组 | 改良本体、地形限制、光环范围 |
| 总督组 | 基础能力 + 各阶晋升 |
| 政策组 | 每张政策的效果与条件 |
| 项目组 | 项目完成效果 |
| UI 面板组 | 每个面板的状态机与数据绑定 |
| 系统/机制组 | 跨实体资源循环、状态机、演出/动画系统等 |

规则：
- **组是计划单位，成员是断言单位**；一个组可以同时包含 Lua、Modifier、UI 三种实现。
- 组数与每组内成员数**因项目规模而异**；上表只示意“组类型”的划分，不要把某个项目的计数当基线。
- **一个项目的 modifier 数量可能远超能力组数；modifier 是证据来源，不是测试单位**。只在“该成员由 modifier 实现”时使用对象列表（`GameEffects`）做附着契约。
- **Modifier 型测试以对象列表为主**：检查“期望的 modifier 是否挂在正确对象上、是否 active、条件/栈/生命周期正确”；官方效果类型默认可信，不强制测数值（见 §4.6）。
- 每个组至少有一位“负责人/状态”，状态四态：`PASS / FAIL / BLOCKED / UNVERIFIED`，不允许空白或默认通过。

## 3. 工作流（8 个阶段）

### 阶段 0：环境与基线（每次会话开始）
- 记录：游戏版本、所有启用 Mod 及 GUID、依赖 DLC、是否加载 DLL/画质 Mod、窗口化配置、Tuner 端口、日志基线。
- 备份：`AppOptions/GraphicsOptions/Mods.sqlite`；记录启用集变化，结束后还原。
- **联机默认不测**：除非用户明确要求联机适配（联机有专门 skill）；本工作流默认单机。
- 判定：任一前置不满足（Mod 未启用、Tuner 不可用、日志不可读）→ 整场 `BLOCKED`，不要开始测试。

### 阶段 1：能力清单（从数据生成，不靠记忆）
- 从 `.CIV`/扩展源码生成组清单与成员清单：每个成员标注**实现类型**（Lua / Modifier / UI / 混合）和**触发入口**。
- 输出：`能力组 → 成员 → 实现类型 → 预期可观测点`。
- 检查：每个 CIV 实体/Modifier/UI 上下文至少映射到一个组；未映射项必须显式列入 `待分类`。
- **先查知识库**：设计前用 `modgen skill "<主题>"` 检索已有知识（property/存档、队列接口、modifier 时序等），并在用例里引用来源；大型项目知识多但难看见，用例必须留下“依据文件/章节”，缺失的知识登记为待补。

### 阶段 2：风险分级与抽样
- P0：阻塞/主线（加载、开局、文明/领袖核心、会导致游戏崩溃或死档）。
- P1：特色能力与 UI 主路径。
- P2：边缘组合、AI/多人/旧档。
- 每组至少测 P1 主路径；P0 每轮全测；P2 按发布节奏滚动。

### 阶段 3：测试设计（契约先行）
每个成员写一条“测试契约”：
```
触发（Given/When）
预期（Then：状态/数值/UI）
断言（可执行查询或截图判据）
负向（不应发生什么）
边界（0/上限/多实例/死亡/失地/读档）
证据（快照字段、日志 marker、截图）
```

### 阶段 4：夹具准备（复用优先）
把“构造场景”的代码与“断言”分离，形成夹具库：
开局/授科技市政/建城/生产区域/生成单位/总督链/政策/战斗/回合推进/UI 点击/数据注入。
要求：夹具本身有冒烟测试；夹具失败记为 `BLOCKED`，不能算被测能力失败。
- **队列/购买优先用 Lua 控制接口**（`CityManager.RequestCommand/RequestOperation`、`UI.RequestPlayerOperation` 等，内置可行性校验），不必走 UI 点击；UI 只用于必须验证按钮常驻/状态机/文案的场景。
- 单位构造：**生产队列优先**；可以先建造再转移单位（卡动画但不影响数据）；不要用 `UnitManager.InitUnit` 绕过限购/优先级检查（生成单位常有不落地/状态异常，且 InitUnit 天然绕过 Lua 检查）。

### 阶段 5：执行（一局多用例）
- 一个会话按“状态变化从小到大”排序（先只读/轻状态，后宣战/建城/存档），同一状态可连续断言多个成员。
- 每条用例：`前置校验 → before 快照 → 动作 → after 快照 → 断言 → 日志检查 → 复位（或标记不可复用）`。
- 失败立即取证（截图、日志切片、状态 JSON），不要继续猜。

### 阶段 6：判定（见第 4 节）

### 阶段 7：防漏判审查（见第 5 节）

### 阶段 8：归档与回归
- 证据包：用例 ID、命令、期望/实际、JSON、截图、日志切片、结论。
- 基线：把关键断言存为回归基线；下轮直接对比。
- 报告只汇总，不替代证据；未测项必须带原因与后续计划。

## 4. 怎么判断结果（判定规则）

### 4.1 四态定义

| 状态 | 条件 |
|---|---|
| **PASS** | 声明的全部断言成立；无新增 `Runtime Error`/`Database` 错误；证据完整可复现 |
| **FAIL** | 任一断言不成立，或出现新增错误；记录失败 hop（哪一跳） |
| **BLOCKED** | 前置/夹具/工具不可用，无法执行；写清缺什么、需要谁补 |
| **UNVERIFIED** | 本轮未测或无法自动判定；写清“为什么、谁、怎么测” |

**PASS 的必要条件**：正向断言 + 至少一条负向断言 + 证据链完整。只有正向没有负向，最多算“部分通过”。

### 4.2 断言类型与判据

| 类型 | 判据 | 示例 |
|---|---|---|
| 等值 | 精确相等（整数/枚举） | `<Mod 计数器> == <期望值>`（键名以 Mod 源码为准） |
| 范围 | 在闭区间/统计范围内（随机） | 信仰增量 ∈ [base/2, base*1.5] |
| 集合 | 包含/相等/差集（modifier 附着） | 期望 attach 集合 ⊆ 实际；多出的显式审查 |
| 差分 | before/after 变化量（注意同回合不重算） | 生产力 +amount×bonus |
| 存在性 | 对象/建筑/单位存在或不存在 | 系统/任务专属建筑出现/移除 |
| 日志 | marker 出现/不出现；**marker 必须与状态断言配对** | `<marker 文本>` 且文化/生产力确实变化 |
| UI | 可见/隐藏/页签/禁用/文本/数值 | 面板打开后卡片数量=3 |
| 错误 | 错误计数为 0 或白名单 | `Runtime Error` 计数=0 |

### 4.3 随机性与时间

- 随机效果：固定多次采样（≥3 次）或断言范围；记录随机源（`Game.GetRandNum` 的调用点）。
- **modifier 时序**：部分 modifier 下回合才生效。先测本回合、再测下一回合：本回合生效即通过；本回合无、下回合有也通过；两回合都无才失败。下回合测量要避免其他状态变化（不要额外结束多回合/触发其他产出），否则数据无法归因。
- 回合边界：明确“动作发生在 turn N，断言在 turn N 还是 N+1”；同回合不重算的产出要跨回合再断言。
- 存档：property 入档、临时变量不入档；跨回合/存档结论以 property 为准。没有明确要求时不单独做读档专项。
- **异常处理**：异常就是 bug，不做“次数回滚/补偿”类验收；断言只允许“无新增错误”。


### 4.4 失败定位（链式断言）

混合能力按 hop 分解：`UI/触发 → 命令/事件 → GP 状态/属性 → 修改器附着 → 效果/UI 显示`。失败时记录“哪个 hop 不符合”，而不是只写“功能无效”。

### 4.5 伪通过清单（判定时逐条打勾排除）

- [ ] 只验证了日志/按钮，没有验证状态或数值
- [ ] 只验证初始值，没有验证后续变化
- [ ] 只测一次成功，没有测负向/边界
- [ ] 没有对照（无法排除“本来就能”/“其他 Mod 干的”）
- [ ] 只在本地玩家上测，未说明 AI 侧是否覆盖（联机默认不测）
- [ ] 用“模拟 Lua/静态推断”替代引擎行为
- [ ] 随机结果只测到一次落在范围内
- [ ] UI 外观正确但数据绑定/数值未验证
- [ ] 忽略日志中的 `Runtime Error`（尤其是被 pcall 吞掉的）
- [ ] 未测项被写成“一致/应该没问题”
- [ ] Modifier 型成员只测了“效果数值不为 0”，没有查对象列表确认挂对了对象
- [ ] 为验证不可见 modifier 去构造复杂数值场景（应先查对象列表，数值只在必要时抽样）

### 4.6 Modifier 型能力的判定：对象列表优先（前置信任）

**信任模型（重要，决定测试成本）**：
- **官方 EffectType 的实现默认可信**：只要 modifier 挂到了正确对象、owner/collection 正确、条件满足且 active，就视为效果已生效；不要求逐个测数值。
- **要测的是“对象正确性”**：owner 类型（player/city/unit/district/plot）、subjects/tracked objects、active、requirement 状态、栈/一次性/永久、生命周期（条件消失后是否移除）。
- **例外（必须测效果/需人工判断）**：
  - 自定义 EffectType/ModifierType（无官方先例可依赖）；
  - 语义不明或新写法的 modifier；
  - 明显可疑的绑定（例如效果是“区域 +1 生产力”却挂给 player）——这类“对象错但也有 modifier”不能算通过；不过这种明显逻辑错误应在**审查第一步（静态绑定检查）**就发现，测试只做兜底。
- 因此多数 modifier 能力的测试动作是：**构造前置状态 → 读取对象 modifier 列表 → 断言“期望集合存在且 active、owner/subjects 正确、无残留”**；数值快照仅在例外或验收要求时使用。

**怎么读对象列表（GameCore_Tuner，`GameEffects`）**：

```lua
-- 全部实例 → 过滤我们关心的定义（ModifierId）与 owner
for _,inst in ipairs(GameEffects.GetModifiers()) do
    local def = GameEffects.GetModifierDefinition(inst)   -- .Id/.Type/.OwnerRequirementSetId/.IsRunOnce/.IsPermanent
    local owner = GameEffects.GetModifierOwner(inst)      -- player/city/unit/district/plot 对象
    local active = GameEffects.GetModifierActive(inst)
    local subjects = GameEffects.GetModifierSubjects(inst) or {}
    local tracked = GameEffects.GetModifierTrackedObjects(inst) or {}
    -- 只输出我们 ModifierId 前缀/白名单
end
-- 条件排查：GetModifierOwnerRequirementSet / GetRequirementSetInnerRequirements / GetRequirementState
```

**期望集合从哪来**：
- CIV 的附件表：`TraitModifiers`、`LeaderTraits`、`BuildingModifiers`、`DistrictModifiers`、`ImprovementModifiers`、`PolicyModifiers`、`GovernorPromotionModifiers`、`UnitAbilityModifiers`、`BeliefModifiers` 等；
- 嵌套：`EFFECT_ATTACH_MODIFIER` 的内层 modifier 必须在目标对象上出现（且 owner/subject 符合设计）；
- 由“能力组→成员”清单生成“场景 → 期望对象集合”的契约。

**判定规则**：
| 结果 | 判定 |
|---|---|
| 期望集合在正确对象上存在且 active | PASS（官方效果默认可信） |
| 缺失 / owner 错误 / subject 错误 / active=false（因条件/collection 错） | FAIL |
| 条件消失后残留、重复叠加超栈、run-once 多次触发 | FAIL |
| 多出未预期 modifier | 需解释：显式审查后可为 PASS（有正当来源）或 FAIL |
| 自定义/不确定效果 | 追加数值/行为抽样，抽样结果作为补充断言 |
| 无法枚举（上下文/API 不可用） | BLOCKED，先修工具或换状态 |

**报告记录**：对象列表 dump 要过滤并保留“定义 Id + owner 类型/id + active + 条件状态”；不要贴几千行原始实例。

## 5. 怎么避免漏判（本工作流的核心）

### 5.1 三层覆盖矩阵

对每个能力组维护：

```
组 → 成员 → 覆盖维度（触发/负向/范围/时序/叠加/多实例/边界/AI/多人/存档/UI 状态）
```

每个成员至少：1 正向 + 1 负向；凡涉及 modifier 的成员，额外记录“预期 owner/collection/active 条件”。

### 5.2 双向完备性检查（机器可查）

- **数据 → 组**：每个 CIV 实体/Modifier 定义/UI 上下文必须至少出现在一个组里；未映射项输出清单。
- **组 → 断言**：每个组必须有成员清单和断言；没有断言的成员标 `UNVERIFIED`。
- **断言 → 证据**：每条断言必须有可执行查询或截图判据；没有判据的不算测试设计。
- **对象列表契约**：每个 modifier 型成员必须有“定义 Id → 期望 owner 类型/对象、subjects、active 条件、栈/一次性/永久”；写不出对象的 modifier 视为未设计。
- 每次构建后自动跑这些清单；缺失项数量是“漏测指数”，不是“报告字数”。

### 5.3 细节维度清单（设计阶段逐维勾选）

1. **触发条件**：科技/市政/战争/地形/地貌/资源/宗教/政体/城邦/领袖过滤。
2. **范围/归属**：self/unit/city/player/all cities/plots；modifier 的 owner/collection/subjects 与设计一致。
3. **时序**：回合开始/结束、首次激活、建筑完成、政策切换、时代变化、读档。
4. **叠加语义**：stack limit / refresh / permanent / run-once / 多来源。
5. **多实例**：2 城、2 单位、多改良、多政策。
6. **边界**：0/负/上限/满值/单位死亡/城市失地/易主/建筑被劫掠。
7. **负向**：条件不满足时不应发生（错误领袖/错误地块/未交战/无次数）。
8. **AI 侧**：AI 是否结算（看海）；联机默认不测（除非用户要求）。
9. **UI 状态**：空态/有数据/禁用/冷却/页签/ESC/重开后；不可用按钮通常**隐藏**而非“禁用但可见”（以源码/约定为准）。
10. **持久化**：跨回合/存档数据看 property；临时变量不入档。
11. **构建/部署**：生成 SQL 与安装版哈希一致、modinfo 无临时路径。
12. **文本/图标**：可见界面用的 LOC 非空、图标存在。
13. **静态绑定预检**（审查第一步）：effect 的作用域与 owner/collection 是否自洽；明显错误（如“区域 +1 生产力”挂给 player）静态先抓，测试只兜底。

### 5.4 评审机制

- 测试设计由“作者以外的人/Agent”按 5.3 清单复核一次；
- 测试结果必须包含“未测清单及原因”，评审时先看未测项，再看通过项；
- 任何“降级/延后”必须给出复测计划；禁止把未测项默认合并为通过。

### 5.5 度量（看覆盖，不看“跑了多少”）

- 能力组覆盖率 = 有状态（PASS/FAIL/BLOCKED/UNVERIFIED）的组 ÷ 总组；
- 断言密度 = 断言数 ÷ 成员数（<1 说明只是“看过”）；
- 未映射实体数（目标 0）；
- 四态分布与 FAIL 复发率；
- 漏判率 = 发布后发现的“本该测到但未测”的问题数。

## 6. 测试用例与结果记录模板

### 6.1 用例模板（Markdown/YAML 均可）

```yaml
case_id: CASE-<组>-<序号>
group: 领袖能力组 / <领袖名>
members:
  - id: GOV-M1
    impl: modifier
    trigger: 总督在城 + 有可购买单位
    expect: 城市可信仰购买 CLASS_... 单位
    assert:
      - property('<Mod 键>') == <期望值>
      - purchase 成功，faith 减少 cost
      - GameEffects: 期望 attach 集合 ⊆ 实际（owner=city）
    negative: 无总督城市同参数购买失败
    boundary: 信仰不足 / 无可用单位 / 总督未就职
evidence: [json_snapshot, log_marker, screenshot_before_after]
status: PASS|FAIL|BLOCKED|UNVERIFIED
```

### 6.2 结果记录模板

```
用例 / 成员 / 前置校验 / 动作 / 期望 / 实际 / 证据路径 / 结论 / 失败 hop / 备注
```

每条记录必须能回答：**期望从哪来、实际从哪读、证据在哪、如果失败是哪一跳**。

## 7. 组类型的方法模板（每种能力怎么测）

通用原则：**先确定该组成员的实现类型**（Modifier / Lua / UI / 混合），再选最小工具；Modifier 型用对象列表，Lua 型用属性/日志，UI 型用 `DoLeftClick` + 截图；混合链路分跳断言。

### 7.1 文明能力组
- **目的**：文明特性绑定正确、系统入口存在。
- **驱动**：开局该文明（本地玩家）。
- **断言**：`GameInfo.CivilizationTraits` 绑定；期望 modifier 集合挂在 owner=player 上且 active（对象列表）；系统属性/计数器初值；负向：非该文明不触发。
- **不测**：官方 modifier 的数值效果（信任模型），除非自定义类型或绑定可疑。

### 7.2 领袖能力组
- **目的**：领袖特性/脚本事件/专属按钮。
- **驱动**：开局该领袖；按成员触发（战斗、回合开始、城市/单位按钮）。
- **断言**：领袖绑定属性；Lua 事件的属性/单位经验/伤害/地块产出（状态断言）；若领袖 Trait 有 modifier，查 owner=player 对象列表；UI 按钮用 `DoLeftClick` + 控件状态/截图。
- **负向/边界**：错误对象（城市/区域攻击者）、条件不满足、非军事单位、首次激活只一次、上限与溢出。
- **示例**：`CASE-<组>-LEADER-01`（L-A 战斗、L-B 回合开始、L-C 城市按钮）。

### 7.3 特色单位组
- **目的**：单位本体、固有能力、主动技能、限购/限造、次数与生命周期。
- **驱动**：生产/购买队列（Lua 控制接口，自带可行性校验）；不要用 `InitUnit` 造场景。
- **断言**：单位存在与属性（`ActionCharges`/移动力/形态）；单位能力效果（属性/日志/UI）；owner=unit 的 modifier 列表；限购：第二次生产/购买请求应失败（看队列结果与单位数）；主动技能按钮状态（隐藏/可用）与点击后状态变化。
- **负向/边界**：非该单位、无移动力/次数（通常隐藏按钮）、非己方城市地块、第二次购买、随机范围。

### 7.4 特色区域组
- **目的**：区域本体、区域能力、附属建筑链、区域级 modifier。
- **驱动**：生产队列（`CreateIncompleteDistrict` + `FinishProgress`）或正常建造；不要依赖 WorldBuilder 直接放置（可能不触发附件 modifier）。
- **断言**：`city:GetDistricts():HasDistrict/GetNumDistricts`；owner=city 的 modifier 列表（区域附件/计数属性）；区域相关属性（如 `<属性键>`，键名以 Mod 源码为准）；负向：前置市政/地块不合法/重复。
- **效果**：除非自定义/数值验收要求，不构造产出快照；以对象列表主证。

### 7.5 特色建筑组
- **目的**：建筑存在、附件 modifier、替代/前置/连锁、InternalOnly 虚拟建筑。
- **驱动**：生产/购买队列；InternalOnly 建筑由 Lua 创建时用 `HasBuilding` 断言存在/移除。
- **断言**：`city:GetBuildings():HasBuilding`；owner=city 的 modifier 列表；建筑链（被替代建筑不存在/新建筑存在）；负向：前置未解锁、已拥有、时代过时。
- **注意**：InternalOnly 建筑不进入可见 UI，但数据与 modifier 必须验证。

### 7.6 改良组
- **目的**：改良放置、地形/资源限制、改良附件 modifier、光环范围。
- **驱动**：建造者/`WorldBuilder.MapManager():SetImprovementType` 放置（模型/外观可用 WorldBuilder；功能验收尽量走建造者）。
- **断言**：`plot:GetImprovementType`；owner=plot/city 的 modifier 列表；光环覆盖的地块集合/属性；负向：地形不合法、未完工、被劫掠。

### 7.7 总督组
- **目的**：基础能力、各阶晋升、赴任/就职时序、互斥/开放。
- **驱动**：`UI.RequestPlayerOperation` APPOINT/ASSIGN/PROMOTE；就职需等回合（`IsEstablished`/属性门槛）。
- **断言**：owner=city（或 player，按设计）的 modifier 列表按晋升层级出现且 active；城市属性/建筑/单位变化；卸任/换城后 modifier 移除（生命周期）；负向：未就职、重复晋升、互斥总督。
- **注意**：晋升 modifier 的 owner 语义是本组最容易错的点，对象列表能直接看出。

### 7.8 政策组
- **目的**：政策槽位绑定、效果 modifier、切换/移除。
- **驱动**：政策激活夹具（需先 spike：政策槽/政体 API 或 UI 操作）。
- **断言**：owner=player 的 modifier 列表出现；卸下政策后消失；负向：未激活、切换后残留。

### 7.9 项目组
- **目的**：项目完成、一次性效果、重复/取消。
- **驱动**：生产队列项目完成。
- **断言**：项目计数/完成状态；相关 modifier 或属性；负向：取消/重复完成。

### 7.10 UI 面板组
- **目的**：面板可打开、状态机、数据绑定、点击链路。
- **驱动**：`Control:DoLeftClick()` 打开/切页/操作；用 `SetHasMet`、属性、GP 函数注入真实数据；不要用 `SetHide(false)` 代替 Open/Refresh。
- **断言**：`ContextPtr`/`Controls` 的可见/隐藏/禁用/文本/数量；点击后的 GP 状态/属性变化；前后截图；负向：空态、禁用、ESC、重开、数据边界。
- **不测**：modifier（除非面板只是触发链的一跳）。

### 7.11 系统/机制组（跨实体资源循环、状态机、演出/动画系统等）
- **目的**：跨实体系统的状态机、资源循环、联动与边界。
- **驱动**：属性状态机 + 回合推进 + UI；可结合看海 AI 做长时回归。
- **断言**：状态/属性流转（初始→激活→持续→结束→冷却）、相关对象 modifier 列表、UI 状态；混合链路分跳断言（UI→命令→GP 属性→附着→效果）。
- **负向/边界**：上限、冷却、提前结束、读档（如需要）、AI 侧不触发 UI 的边界说明。

## 8. 长期解法：Modifier / Requirement 测试知识库（Playbook）

这是“按能力组”之外的第二个杠杆：**效果类型与条件类型是有限的，可以一劳永逸地积累测试方法**。

### 8.1 卡片结构（每个类型一张）

```
Type: EFFECT_/REQUIREMENT_/COLLECTION_/MODIFIER_
语义：
官方可信度：官方效果（默认可信）/ 自定义（需抽样）
期望对象：owner 类型（player/city/unit/district/plot）、subjects/collection 合法性
条件/时序：reqset、下回合生效、栈/一次性/永久
对象列表断言：用 GameEffects 查什么（定义 Id → 期望对象/active/条件）
可观测点（仅例外时需要）：API/属性/快照/日志
触发夹具：
负向/边界：
已知坑：
证据样例：
最近验证版本：
```

### 8.2 覆盖与优先级

- 从游戏库里枚举全部 `EffectType`、`RequirementType`、`CollectionType`、`ModifierType`，生成空卡片清单与覆盖看板。
- 优先级：本 Mod 使用的自定义类型 → 使用频率最高的原版类型（yield/combat/attach/purchase/requirement collection）→ 其余。
- 一个大型 Mod 的 modifier 可以多达数百个，通常只落在几十个类型上；**类型卡写完后，新 Mod 的 modifier 测试成本会显著下降**。
- 卡片的首要价值是“**这个类型该挂给谁、怎么用对象列表验证**”，而不是“怎么测出数值”。

### 8.3 与工作流结合

- 测试设计时，成员“实现类型”直接查卡片，得到“用什么夹具、怎么断言、有什么坑”；
- 新发现的坑回写卡片；
- 游戏版本更新后按卡片跑一遍冒烟，卡片即回归用例。

### 8.4 与人/Agent 分工

- Agent 负责生成卡片骨架、执行夹具、收集证据、更新“最近验证版本”；
- 人负责确认语义与验收口径（Oracle）；
- 卡片既是知识库，也是测试资产，不应埋在某次会话的脚本里。

## 10. 反模式（写测试时最容易犯）

1. 把“跑起来没报错”当“功能正确”。
2. 只测 UI 外观，不测数据绑定。
3. 只测初始状态，不测变化后的状态。
4. 用模拟 Lua/静态推断代替真机引擎。
5. 无对照就宣布能力生效。
6. 只测本地玩家，默认 AI 侧“应该一样”（联机默认不测，除非用户明确要求）。
7. 忽略随机范围与同回合不重算。
8. 未测项不登记，报告只写“已检查”。
9. 用 `UnitManager.InitUnit` 生成单位来构造场景（绕过限购/优先级检查，且常见坐标/状态异常；优先生产/购买队列）。
10. Modifier 型成员只测“效果数值不为 0”，不去查对象列表（挂错对象、条件未满足也看不出来）。
11. 为不可见 modifier 硬构造复杂数值场景（应先查对象列表；数值只在自定义/不确定效果时抽样）。
12. 把每个 modifier 都当独立测试任务，成本爆炸后开始抽样漏测。
13. 测试脚本、断言、证据散落在会话里，下次无法重放。

## 11. 最小落地路线（建议）

1. 选一个你已经过实战验证的组（例如某个领袖组）作为**样板**：按本文模板补全“成员 → 断言 → 证据 → 覆盖矩阵”，证明格式可用。
2. 建“组清单生成器”（从 CIV 输出组/成员/实现类型）与“双向完备性检查”。
3. 建 modifier 探针 + 快照/差分（先覆盖该样板组用到的类型）。
4. 把样板组的证据包做成回归基线，再复制到相邻组。
5. 每轮发布只扩大一类组；未测清单必须随报告交付。
