# 明日方舟文明6系列规范

这是用户确认的长期系列约定，适用范围仅为明日方舟题材的文明6 Mod。后续新建、修改、改名和重新生成明日方舟工程时，默认应用本规范，无需用户再次提醒。用户在当前任务明确指定的命名例外优先；设计稿内部标题、文件夹名、版本编号和生成器默认值不构成命名例外。

可爱领袖包使用下表的完整格式；其他明日方舟子系列沿用“明日方舟：角色或主题”的标题格式、对应系列短简介及编号与标题分离的原则，保留该子系列已确认的系列名和文件前缀。其他题材 Mod 不应用本规范，也不把这些系列偏好加入通用 ModTools 制作规则。

制作机制仍遵循当前 ModTools 仓库的 AGENTS.md、skills/RULES.md、skills/WORKFLOW.md 与 modgen/AGENTS.md；本技能不另建一套游戏实现规则。

## 按任务读取

- 名称、简介与地名：继续阅读本文件。
- 封面、英文补全、工坊描述、上传前准备：另读 [发布准备](references/release-preparation.md)。按“玩法中文定稿 → 英文全量补齐 → 封面和双语工坊文本 → 编译核对”执行。用户在当前任务提前要求英文时遵从其要求。
- 封面使用 [原始 PSD 模板](assets/leader-cover.psd) 和 [排版脚本](scripts/render_cover.py)。脚本负责尺寸、图层、字体和输出检查；人物居中、裁切和小图可读性必须由视觉模型或人工复核。

此目录为仓库内可分享版本；个人技能目录只作为安装副本。更新时同步两处，角色素材、单个 Mod 的配方和成品放在该 Mod 工作目录，不混入通用技能。

## 先读真实系列参考

用户指定参考版本时，实际读取该版 `.CIV` 的基础信息和 `.civ6proj` 的 Name、Teaser、Description、LocalizedTextData。不要只凭文件夹名推测显示名，也不要把工程编号拼进面向玩家的标题。

本机参考入口：

- 工具与既有工程：`<ModTools目录>`，其中 `20.0.CIV` 是已核对的参考。
- 可编辑系列工程：`%USERPROFILE%\Documents\Firaxis ModBuddy\Civilization VI\Arknights_Cute_Leaders_<版本>\Arknights_Cute_Leaders_<版本>\Arknights_Cute_Leaders_<版本>.civ6proj`。
- 角色设计：`<本机资料目录>\projects`，优先读取当前角色的选人说明、角色资料和玩家能力文本。

这些是本机定位线索；路径变化时查找当前工程，不新建虚构参考。

## 可爱领袖包的展示文本

已核对 20.0、21.0、22.0，并在 23.0 应用的统一格式：

| 字段 | 约定 | 20.0 实例 |
|---|---|---|
| 中文 Mod 名 | `明日方舟：<代号>（<真名>）` | 明日方舟：乌啾（乌克西克） |
| 中文 Teaser / Description | 两者同为 `明日方舟可爱领袖包 · <代号>（<真名>）` | 明日方舟可爱领袖包 · 乌啾（乌克西克） |
| 英文 Mod 名 | `Arknights: <官方英文代号>` | Arknights: Ukusik |
| 英文简介 / 描述 | `Arknights Cute Leaders: <官方英文代号>` | Arknights Cute Leaders: Ukusik |
| 文件基名 | `Arknights_Cute_Leaders_<版本>` | Arknights_Cute_Leaders_20.0 |

21.0 对应“绮良（云母）”和 Kirara；22.0 对应“水灯心（布莉吉）”和 Brigid；23.0 对应“雪猎（茱安娜）”和 Snow Hunter。23.0 的中文名称为“明日方舟：雪猎（茱安娜）”，简介与描述均为“明日方舟可爱领袖包 · 雪猎（茱安娜）”。后续角色按资料核实，不能复制这些角色身份。

- 真名未知或与代号相同时，省略重复括号；不要编造真名。多人包或其他明日方舟子系列按用户指定的同类样本处理，不硬套单角色格式。
- 简介保持系列短句。详细能力、依赖说明和实现细节写在对应玩家说明、百科或交付文档，不自行把它们塞进短简介。
- 系列编号与显示标题分离。工程编号、GUID、ModVersion 和 Type 中缀各有用途；编辑已有工程时保留其 GUID、Type、依赖和已验证的单人/多人能力，不能从历史参考整体复制。

## 角色与城市名称

- 有真名时，文明显示名用干员代号，领袖显示名用真名；无可靠真名时两者使用代号。工程已有用户确认的特殊命名时以该确认优先。
- 城市名尽可能全部使用明日方舟已出现的地名。先选角色关联地名，不够时扩展到泰拉其他地区，相关性不是硬限制。
- 优先选择城市、城镇、郡和聚落。可按用户允许使用更广义地区，但不要为了凑主题自行造出“牧歌原”“渡水营”一类地名，也不要将同一地名的别称当作不同城市凑数。
- 从当前角色资料、原作文本或可靠资料核对中文写法。可用 [PRTS 地理一览](https://prts.wiki/w/泰拉大典:地理) 定位；有疑义时回查剧情来源。保留项目实际采用的名称清单和来源。
- 修改城市列表时，同时检查文明 `city_info` 与领袖 `capital_name`，以及生成的 CityNames 引用和中文文本；不要只改其中一处。不要把 22.0 的首都或 30 个城市数量当作所有作品的规定。

## 题材素材、组件名称与玩家文本

- 场景背景优先从明日方舟原作剧情图、场景图与已有素材库中选择，先核对角色、地域和画面适配，再考虑生成图片。不要仅因为能生成图片就跳过原作素材；缺少合适素材时可采用其他方案，并记录来源。此偏好针对背景，不禁止其他用途的生成美术。
- 有皮肤立绘时优先采用皮肤；外交前景使用未精英化的初始立绘。选人前景槽若造成顶部留白或人物显示不全，可将皮肤构图放入背景槽，前景使用用户指定的透明空白图。用户已确认的槽位策略优先于一般背景偏好；不为套用剧情背景规则而覆盖已有选择。
- 单位、改良、建筑和区域名称优先查找原作已有的职业、设施、物件与组织称呼，并核对它与组件玩法的关系。找不到合适名称时允许贴合角色背景的原创名称；不要硬套不相关专名，也不要把原创名称描述为原作专名。城市名继续遵守上文地名规则。
- 能力短描述保留触发条件、范围、收益、关键限制；地形数值表、取整规则、分类口径放百科，当前城市的计算明细放面板。脚本同步、原生预览缺项、测试限制放交付说明。不得为了缩短文本而混淆商路产出与城市产出、一次性与持续收益、叠加与替换。
- 明日方舟系列的历史时刻保留源图原色，不添加黄色/棕黄色滤镜、复古双色映射或黄色正片叠底。沿用模板的裁切和透明边缘，从原色源图重新导出，检查最终 PNG/DDS；原图本身为灰度时保留灰度，不虚构颜色。此条仅用于明日方舟系列，其他题材仍按其设计处理。注意现有 `modgen image render` 的 moment 配方默认做双色映射，单纯省略 tone 不会保留原色，应使用保留 RGB 的模板合成流程后导入图片槽。

## 用户要求能力评审时

- 数值以实际过往同系列工程为基准，结合启动时点、投入、覆盖范围、叠加速度和上限比较。不要仅以高于原版判定失衡；区分纸面推算与实机结果。
- 分别说明设计趣味、系列内强度和实现准确性。等效实现要求触发、作用对象、时点、持续性、叠加及与其他效果的交互一致；只让某个算例总收益接近不算等效。奖励从商路挪到城市、持续收益改为回合补发等变化不能默认为等效。
- 对照最新设计与用户确认逐项核对；用户接受的新规则应标作设计调整，不反过来宣称原规则已被等效实现。将确定偏差、规则歧义和待实机验证项分开，静态装载与模拟测试不能证明原生效果和事件时序。

## 工程元数据与交付

新增文明还必须完成通用文化美术检查：读取 ModTools 仓库的 `skills/reference/art/civilization-art.md`，通过原生美术页填写城市/建筑文化与单位文化，并核对 `Cultures.artdef` 的目标文明成员和 Art.xml 引用。此项属于所有新增文明 Mod 的通用要求；不要将其他作品的固定文化风格当作明日方舟系列规定。

在 `.CIV` 的 `workspace.基础信息.data.project_info` 维护 `mod_name`、`teaser`、`description`；`name_raw`、`teaser_raw`、`description_raw` 需对应本版 LOC。可爱领袖包的键形如 `LOC_ARKNIGHTS_CUTE_LEADERS_22_0_NAME` 与 `_DESCRIPTION`，简介和描述共用后一个键。

通过工程工具保留/生成 `localized_text_data` 的 `zh_Hans_CN` 和 `en_US` 元数据。当前生成器会优先保留 `teaser_raw`，所以仅更新 `teaser` 会留下旧简介。英文代号应核实；补齐 Mod 列表的英文元数据不代表整个 Mod 已完成英文翻译。

修改回到 `.CIV` 源工程，再用 modgen 生成绑定的 ModBuddy 工程，不手改生成文件。用户要求工程文件时，交付到已绑定或指定的 ModBuddy 文件夹；编译、安装、部署另按用户要求执行。备份已有工程，保留扩展源码。

生成前同步七个字段：`mod_name`、`teaser`、`description`、`name_raw`、`teaser_raw`、`description_raw`、`localized_text_data`。不要只修导出文件，或只改中文名称而留下旧 Teaser。

最后实际解析生成的 `.civ6proj`，检查 Name 使用本版 `_NAME`，Teaser 与 Description 共用本版 `_DESCRIPTION`，两种语言的文本符合上表，标题没有工程版本号，简介没有能力长文、依赖说明、旧版本 LOC 或文件名占位，并执行当前流程要求的 validate / project-check。报告本次修改及验证结果，不将静态检查表述为游戏内验收。
